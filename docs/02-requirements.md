# 02. Требования: ShopCore

> Статус: черновик v0.1 · Автор: Дарья Корепанова · Основа: [01-vision.md](01-vision.md) v0.2

## 1. О документе

Документ описывает, **что** должна делать система: функциональные требования в виде user stories с критериями приёмки и нефункциональные требования с измеримыми значениями. **Как** это устроено (таблицы, методы API, диаграммы), описано в документах 03–06.

**Формат user story:** «Как ‹роль›, я хочу ‹действие›, чтобы ‹ценность›».

**Критерии приёмки (AC)** — проверяемые условия: story считается готовой, только когда выполнены все её AC. По ключевым сценариям AC дополнительно расписаны на Gherkin (раздел 4); из них потом получаются автотесты.

**Приоритет:** MoSCoW, как в vision. **Ссылки:** UC — сценарий из vision, BR — бизнес-правило из vision.

Коды ошибок (`OUT_OF_STOCK`, `INVALID_TRANSITION` и т.д.) указаны для ясности. Полный каталог ошибок и HTTP-коды — в `04-api.md`.

## 3. Функциональные требования

### E1. Аккаунт

#### US-01. Регистрация

Как **покупатель**, я хочу зарегистрироваться по email и паролю, чтобы оформлять заказы и видеть их историю.

UC-01 · Must

1. Регистрация по email и паролю. Email уникален без учёта регистра: `Anna@mail.ru` и `anna@mail.ru` — один и тот же адрес.
2. Пароль: не короче 8 символов, содержит хотя бы одну букву и одну цифру. Иначе — ошибка валидации с описанием нарушенного правила.
3. Email уже занят → ошибка `EMAIL_TAKEN`, новый пользователь не создаётся.
4. Пароль хранится только в виде хеша (bcrypt), в открытом виде нигде не сохраняется и не логируется.
5. Новый пользователь получает роль `customer`. Роль `admin` через регистрацию получить нельзя, администраторы создаются только сидом или вручную.
6. Подтверждение email — вне скоупа.

#### US-02. Вход и продление сессии

Как **пользователь**, я хочу войти и не вводить пароль при каждом запросе, чтобы спокойно пользоваться магазином.

UC-01 · Must

1. При верных email и пароле выдаются два токена: access (живёт 15 минут) и refresh (30 дней).
2. При неверном email **или** пароле ответ одинаковый: «Неверный email или пароль». Система не сообщает, что именно неверно.
3. По действующему refresh-токену выдаётся новый access-токен.
4. Запрос с истёкшим или поддельным access-токеном → `401`.
5. Больше 5 неудачных попыток входа с одного IP за минуту → `429`, следующая попытка возможна через минуту.

### E2. Каталог

#### US-03. Список товаров с фильтрами

Как **покупатель**, я хочу искать и фильтровать товары, чтобы быстро найти нужное.

UC-02 · Must

1. Показываются только товары с `is_active = true`.
2. Фильтры: категория (включая все её подкатегории), цена от/до, поиск по названию без учёта регистра.
3. Сортировка: по цене по возрастанию, по цене по убыванию, сначала новые. По умолчанию — сначала новые.
4. Пагинация: `limit` (по умолчанию 20, максимум 100) и `offset`. В ответе есть общее количество найденных товаров.
5. У каждого товара в ответе: доступный остаток (`quantity − reserved`) и признак «в наличии».
6. Каталог доступен без авторизации.

#### US-04. Карточка товара

Как **покупатель**, я хочу открыть карточку товара, чтобы увидеть подробности и наличие.

UC-02 · Must

1. Карточка содержит: название, описание, категорию, цену, доступный остаток.
2. Несуществующий или неактивный товар → `404`.

### E3. Корзина

#### US-05. Добавление товара в корзину

Как **покупатель**, я хочу складывать товары в корзину, чтобы оформить их одним заказом.

UC-03 · BR-07, BR-08 · Must

1. У каждого покупателя одна корзина; она создаётся автоматически при первом добавлении.
2. Количество одного товара — от 1 до 10 (BR-08). Если товар уже в корзине, количество суммируется, но итог не может превысить 10 → иначе ошибка валидации.
3. Неактивный товар добавить нельзя → `PRODUCT_INACTIVE` (BR-07).
4. Нельзя добавить больше доступного остатка → `OUT_OF_STOCK`. При этом добавление в корзину **не резервирует** товар: окончательная проверка — при оформлении заказа.
5. Корзина показывает **текущие** цены товаров и итоговую сумму. Цена фиксируется только при оформлении заказа (BR-02).

#### US-06. Изменение и очистка корзины

Как **покупатель**, я хочу менять количество и удалять товары из корзины, чтобы собрать нужный заказ.

UC-03 · BR-08 · Must

1. Можно изменить количество позиции в пределах 1–10.
2. Можно удалить позицию. Повторное удаление уже удалённой позиции не считается ошибкой.
3. Если товар в корзине стал неактивным или его доступный остаток меньше количества в корзине, позиция помечается как «недоступна», но из корзины автоматически не удаляется.

### E4. Заказы

#### US-07. Оформление заказа

Как **покупатель**, я хочу оформить заказ из корзины, чтобы товар закрепился за мной на время оплаты.

UC-04 · BR-01, BR-02, BR-09 · Must

1. Заказ оформляется из всех позиций корзины. Пустая корзина → `CART_EMPTY`.
2. Проверки и изменения выполняются **атомарно** (одной транзакцией): либо заказ создан и весь товар зарезервирован, либо ничего не изменилось.
3. Если хотя бы одной позиции не хватает или товар неактивен → `OUT_OF_STOCK` / `PRODUCT_INACTIVE` со списком проблемных позиций; заказ не создаётся, резерв не меняется.
4. Цена каждой позиции копируется в заказ (BR-02). Сумма заказа считается в копейках (BR-09).
5. Заказ создаётся в статусе `created`, срок оплаты — 15 минут (`expires_at`, BR-01). Резерв каждого товара увеличивается на количество в заказе.
6. После успешного оформления корзина очищается.
7. Одновременные заказы не могут зарезервировать больше доступного остатка (цель G1): при гонке за последний товар успешен ровно один заказ.
8. Запрос требует заголовок `Idempotency-Key`. Повтор с тем же ключом и тем же содержимым возвращает тот же заказ, новый не создаётся. Тот же ключ с другим содержимым → `IDEMPOTENCY_KEY_REUSED`. Ключи хранятся 24 часа.
9. Публикуется событие `OrderCreated` и планируется проверка истечения резерва.

#### US-08. Мои заказы

Как **покупатель**, я хочу видеть свои заказы и их статусы, чтобы понимать, что с ними происходит.

UC-04 · Must

1. Список заказов покупателя, сначала новые, с фильтром по статусу и пагинацией.
2. Детали заказа: позиции с зафиксированными ценами, сумма, статус, срок оплаты, история смены статусов.
3. Покупатель видит только свои заказы. Попытка открыть чужой заказ → `404` (а не `403`, чтобы не раскрывать, что такой заказ существует).

#### US-09. Отмена неоплаченного заказа

Как **покупатель**, я хочу отменить неоплаченный заказ, чтобы освободить товар и не получать напоминаний.

UC-06 · BR-04 · Must

1. Отменить можно только заказ в статусе `created` → статус `cancelled`, резерв снимается.
2. Повторная отмена уже отменённого заказа возвращает успех и текущее состояние заказа (идемпотентность).
3. Заказ в любом другом статусе → `INVALID_TRANSITION`. Оплаченный заказ отменяется только возвратом через администратора (BR-04).
4. В истории статусов фиксируется причина: «отменён покупателем».
5. Публикуется событие `OrderCancelled`.

### E5. Оплата

#### US-10. Оплата заказа

Как **покупатель**, я хочу оплатить заказ картой на странице платёжного провайдера, чтобы получить товар.

UC-05 · BR-03, BR-06 · Must

1. Оплатить можно только заказ в статусе `created` с неистёкшим сроком оплаты. Иначе → `INVALID_TRANSITION` / `ORDER_EXPIRED`.
2. Система создаёт платёж в PSP на полную сумму заказа (BR-03) и возвращает ссылку на страницу оплаты.
3. Если у заказа уже есть активный платёж, возвращается его ссылка, новый платёж не создаётся (BR-06).
4. Запрос требует `Idempotency-Key` (правила — как в US-07, AC 8).
5. PSP не ответил за 5 секунд или вернул ошибку → `PSP_UNAVAILABLE`, заказ остаётся `created`, покупатель может повторить попытку.

#### US-11. Обработка уведомления об оплате

Как **система**, я хочу надёжно обрабатывать уведомления PSP, чтобы каждая оплата была учтена ровно один раз.

UC-05 · BR-06 · Must

1. Каждый вебхук проверяется по подписи HMAC-SHA256 от исходного тела запроса. Неверная подпись → `401`, данные не меняются.
2. Вебхук с временной меткой старше 5 минут отклоняется → `401` (защита от повторной отправки перехваченного запроса).
3. **Успешная оплата заказа в статусе `created`** — одной транзакцией:
    - платёж → `succeeded`, заказ → `paid`;
    - со склада списывается количество (`quantity` и `reserved` уменьшаются);
    - запись в истории статусов;
    - в outbox: событие `OrderPaid` и команда `SendReceipt`.
4. **Дубль вебхука** (платёж с этим `provider_payment_id` уже в финальном статусе): данные не меняются, ответ `200`.
5. **Неуспешная оплата:** платёж → `failed`, заказ остаётся `created`, покупатель может попробовать снова до истечения срока.
6. **Сумма в вебхуке не совпадает с суммой заказа:** заказ не меняется, платёж помечается как расхождение, пишется ошибка в журнал для ручного разбора, ответ `200`.
7. **Неизвестный `provider_payment_id`:** данные не меняются, ошибка в журнал, ответ `200` (чтобы PSP не повторял запрос бесконечно).
8. Время от получения вебхука до статуса `paid` — не более 5 секунд в 95% случаев (G4).

#### US-12. Поздняя оплата

Как **покупатель**, который оплатил заказ в последний момент, я хочу получить товар или деньги обратно, чтобы не потерять оплату.

UC-05 · BR-10 · Must

1. Успешная оплата пришла по заказу в статусе `expired`:
    - если доступного остатка хватает на все позиции — заказ переходит в `paid`, товар списывается со склада, в истории причина «поздняя оплата»;
    - если хотя бы одной позиции не хватает — заказ остаётся `expired`, по платежу автоматически создаётся возврат в PSP, покупателю отправляется уведомление.
2. Оплата по заказу в статусе `cancelled` обрабатывается так же, как по `expired`.
3. Каждый такой случай пишется в журнал для контроля.

### E6. Жизненный цикл заказа

#### US-13. Истечение неоплаченного заказа

Как **владелец магазина**, я хочу, чтобы неоплаченный товар возвращался в продажу, чтобы не терять покупателей.

UC-07 · BR-01, BR-11 · Must

1. Через 15 минут после оформления заказ в статусе `created` переходит в `expired`, резерв снимается.
2. Если заказ к этому моменту уже оплачен или отменён, ничего не происходит.
3. Товар возвращается в продажу не позже чем через 1 минуту после истечения срока (G3).
4. Основной механизм — отложенное сообщение в RabbitMQ (TTL + DLX). Резервный — проверка просроченных заказов раз в 5 минут, на случай если сообщение потерялось.
5. В истории причина «истёк срок оплаты». Публикуется событие `OrderExpired`, покупателю ставится уведомление (BR-11).

#### US-14. Уведомления покупателю

Как **покупатель**, я хочу получать письма о важных изменениях заказа, чтобы не проверять его вручную.

UC-11 · BR-11 · Should

1. Письма отправляются при переходе заказа в `paid` (чек), `expired`, `shipped`, `refunded`, а также при автоматическом возврате поздней оплаты.
2. Письмо о событии отправляется не позже чем через 1 минуту в 95% случаев (G5).
3. При ошибке отправки — 3 повтора с паузами 1, 5 и 15 минут. После третьей неудачи сообщение уходит в parking-очередь, ошибка пишется в журнал.
4. Одна команда не приводит к двум письмам, даже если доставлена дважды.
5. Реальная отправка не требуется: в учебной версии письмо пишется в лог в том виде, в каком ушло бы покупателю.

### E7. Администрирование

#### US-15. Управление товарами

Как **администратор**, я хочу заводить и редактировать товары, чтобы каталог был актуальным.

UC-08 · BR-02, BR-07 · Must

1. Создание товара: название, описание, категория, SKU, цена. SKU уникален → иначе `SKU_TAKEN`. Цена больше нуля.
2. Редактирование названия, описания, категории и цены. Изменение цены не влияет на уже оформленные заказы (BR-02).
3. Товар не удаляется физически, а снимается с продажи (`is_active = false`), потому что на него ссылаются заказы (BR-07).
4. Все админские методы доступны только роли `admin`, иначе → `403`.

#### US-16. Управление складом

Как **администратор**, я хочу менять остатки, чтобы они совпадали с реальным складом.

UC-08 · Must

1. Администратор задаёт фактическое количество товара на складе.
2. Нельзя установить количество меньше текущего резерва → `STOCK_BELOW_RESERVED`.
3. Изменение остатка записывается в журнал: кто, когда, было, стало.

#### US-17. Отгрузка и доставка

Как **администратор**, я хочу отмечать отгрузку и доставку, чтобы покупатель видел, где его заказ.

UC-09 · Should

1. `paid` → `shipped` → `delivered`, по одному действию на переход.
2. Любой другой переход → `INVALID_TRANSITION`.
3. При отгрузке покупатель получает уведомление.

#### US-18. Возврат

Как **администратор**, я хочу вернуть деньги за оплаченный заказ, чтобы урегулировать претензию покупателя.

UC-10 · BR-04, BR-05 · Should

1. Возврат возможен только для заказа в статусе `paid` и только на полную сумму (BR-05). Иначе → `INVALID_TRANSITION`.
2. Система отправляет запрос на возврат в PSP и сразу отвечает, что возврат принят в обработку. Статус заказа пока не меняется.
3. Когда PSP подтверждает возврат вебхуком: заказ → `refunded`, товар возвращается на склад, публикуется `OrderRefunded`, покупателю уходит уведомление.
4. Повторный запрос возврата по заказу, для которого возврат уже в обработке, не создаёт второй возврат.
5. Возврат уже отгруженного или доставленного заказа — вне скоупа.

### E8. Аналитика

#### US-19. Витрина продаж

Как **аналитик**, я хочу получать данные о продажах без запросов к рабочей БД, чтобы строить отчёты, не мешая магазину.

UC-12 · Should

1. Витрина строится из событий Kafka и хранится в отдельной схеме `analytics`.
2. Витрина содержит по дням и товарам: количество оплаченных заказов, проданные штуки, выручку в копейках. Возвраты уменьшают показатели.
3. Данные появляются в витрине не позже чем через 1 минуту после события (G6).
4. Повторно полученное событие не искажает витрину.
5. Если перечитать события с начала, витрина получится точно такой же.

#### US-20. Дашборд продаж

Как **владелец магазина**, я хочу видеть основные показатели на одном экране, чтобы быстро оценивать продажи.

UC-13 · Could

1. Выручка по дням за выбранный период.
2. Топ-5 товаров по выручке.
3. Доля оплаченных заказов от оформленных и доля истёкших.
4. Дашборд на Streamlit читает только витрину `analytics`.

## 4. Критерии приёмки на Gherkin

### Оформление заказа (US-07)

```gherkin
Feature: Оформление заказа

  Background:
    Given покупатель авторизован
    And товар SKU-42 активен, на складе 5 шт., в резерве 3 шт.

  Scenario: Успешное оформление
    Given в корзине 2 шт. SKU-42 по цене 1 000,00 ₽
    When покупатель оформляет заказ с новым Idempotency-Key
    Then создан заказ в статусе created на сумму 2 000,00 ₽
    And срок оплаты заказа — через 15 минут
    And резерв SKU-42 равен 5
    And корзина пуста

  Scenario: Не хватает товара
    Given в корзине 3 шт. SKU-42
    When покупатель оформляет заказ
    Then возвращается ошибка OUT_OF_STOCK с позицией SKU-42
    And заказ не создан
    And резерв SKU-42 по-прежнему равен 3
    And корзина не изменилась

  Scenario: Повтор запроса с тем же ключом
    Given покупатель успешно оформил заказ с ключом K1
    When покупатель повторяет тот же запрос с ключом K1
    Then возвращается тот же заказ
    And новый заказ не создан
    And резерв не изменился

  Scenario: Гонка за последний товар
    Given доступный остаток SKU-42 равен 1
    And 20 покупателей держат в корзине по 1 шт. SKU-42
    When все 20 одновременно оформляют заказ
    Then ровно 1 заказ создан
    And 19 покупателей получают ошибку OUT_OF_STOCK
    And резерв SKU-42 равен количеству на складе
```

### Уведомление об оплате (US-11, US-12)

```gherkin
Feature: Обработка вебхука PSP

  Background:
    Given заказ O-1 в статусе created на сумму 2 000,00 ₽
    And по заказу создан платёж P-1 в статусе pending

  Scenario: Успешная оплата
    When приходит вебхук со статусом succeeded по P-1 на 2 000,00 ₽ с верной подписью
    Then ответ 200
    And платёж P-1 в статусе succeeded
    And заказ O-1 в статусе paid
    And товар списан со склада, резерв уменьшен
    And в outbox есть событие OrderPaid и команда SendReceipt

  Scenario: Дубль вебхука
    Given вебхук succeeded по P-1 уже обработан
    When тот же вебхук приходит повторно
    Then ответ 200
    And данные заказа, платежа и склада не изменились
    And новых записей в outbox нет

  Scenario: Неверная подпись
    When приходит вебхук по P-1 с неверной подписью
    Then ответ 401
    And заказ O-1 остаётся в статусе created

  Scenario: Поздняя оплата, товар ещё есть
    Given заказ O-1 перешёл в expired, резерв снят
    And доступного остатка хватает на все позиции O-1
    When приходит вебхук succeeded по P-1
    Then заказ O-1 в статусе paid
    And в истории статусов причина «поздняя оплата»

  Scenario: Поздняя оплата, товара уже нет
    Given заказ O-1 перешёл в expired, резерв снят
    And доступный остаток SKU-42 равен 0
    When приходит вебхук succeeded по P-1
    Then заказ O-1 остаётся в статусе expired
    And по P-1 создан возврат в PSP
    And покупателю поставлено уведомление о возврате
```

### Истечение заказа (US-13)

```gherkin
Feature: Истечение неоплаченного заказа

  Scenario: Заказ не оплачен вовремя
    Given заказ O-2 в статусе created, оформлен 15 минут назад
    When срабатывает проверка истечения
    Then заказ O-2 в статусе expired
    And резерв товаров заказа снят
    And опубликовано событие OrderExpired
    And покупателю поставлено уведомление об отмене

  Scenario: Заказ успели оплатить
    Given заказ O-3 оформлен 15 минут назад и уже в статусе paid
    When срабатывает проверка истечения
    Then заказ O-3 остаётся в статусе paid
    And резерв и склад не меняются
```

## 5. Нефункциональные требования

| ID | Категория | Требование |
| --- | --- | --- |
| NFR-01 | Производительность | Каталог (список и карточка): p95 < 300 мс при 50 RPS. |
| NFR-02 | Производительность | Оформление заказа: p95 < 500 мс. |
| NFR-03 | Производительность | Обработка вебхука PSP: p95 < 1 с; от вебхука до статуса `paid` — p95 ≤ 5 с (G4). |
| NFR-04 | Надёжность | Ни одного заказа сверх доступного остатка при конкурентных запросах (G1); подтверждается тестом «20 параллельных заказов на последний товар». |
| NFR-05 | Надёжность | Ни одной повторно проведённой оплаты (G2); все обработчики вебхуков и сообщений идемпотентны. |
| NFR-06 | Надёжность | Недоступность RabbitMQ или Kafka не мешает оформлять и оплачивать заказы. Сообщения копятся в outbox и отправляются не позже чем через 1 минуту после восстановления брокера. |
| NFR-07 | Надёжность | Гарантия доставки сообщений — at-least-once; каждый consumer устойчив к дублям. |
| NFR-08 | Безопасность | Пароли — только bcrypt-хеш. Секреты (ключи JWT, HMAC) — только в переменных окружения, не в репозитории. |
| NFR-09 | Безопасность | Все вебхуки проверяются по подписи HMAC-SHA256 и временной метке. |
| NFR-10 | Безопасность | Персональные данные в логах маскируются: `a***@mail.ru`. |
| NFR-11 | Данные | Деньги — целые числа в копейках. Время хранится в UTC. |
| NFR-12 | Данные | История статусов заказов и журнал изменений склада не удаляются и не редактируются. |
| NFR-13 | Наблюдаемость | Логи в JSON; в каждой записи `request_id`, а где применимо — `order_id`. |
| NFR-14 | Наблюдаемость | `/health` показывает состояние БД, RabbitMQ и Kafka. Очереди, топики и отставание consumer видны в RabbitMQ Management и Kafka UI. |
| NFR-15 | Сопровождаемость | Схема БД меняется только миграциями. Покрытие тестами бизнес-логики — не ниже 70%. Тесты запускаются в CI на каждый push. |
| NFR-16 | Совместимость API | Версионирование через `/api/v1`. Единый формат ошибок. Спецификация OpenAPI генерируется из кода и совпадает с реализацией. |
| NFR-17 | Развёртывание | Вся система поднимается одной командой `docker compose up` на чистой машине. |

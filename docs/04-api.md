# 04. API: ShopCore

> Статус: черновик v0.1 · Автор: Дарья Корепанова · Основа: [02-requirements.md](02-requirements.md) v0.2, [03-data-model.md](03-data-model.md)

## 1. О документе

Документ описывает контракт HTTP API для разработчиков клиентов: веб-сайта, мобильного приложения, внутренних сервисов. Здесь собраны общие правила (адреса, авторизация, формат ошибок) и подробное описание эндпоинтов каталога, аккаунта и корзины. Заказы, оплата и администрирование перечислены в сводной таблице, а подробно описаны в [05-flows.md](05-flows.md) и [06-integrations.md](06-integrations.md).

Машиночитаемая спецификация генерируется из кода (OpenAPI 3) и всегда соответствует текущей версии:

- Swagger UI — http://localhost:8000/docs
- OpenAPI JSON — http://localhost:8000/openapi.json

Если этот документ и OpenAPI расходятся, источником правды для **форматов** считается OpenAPI, а для **бизнес-правил** — [02-requirements.md](02-requirements.md). Расхождение — дефект, его нужно завести задачей.

## 2. Общие правила

| Правило | Значение |
|---|---|
| Базовый адрес | `http://localhost:8000/api/v1` (кроме `/health`) |
| Версионирование | Версия в пути: `/api/v1`. Несовместимые изменения — только в `/api/v2`. Добавление новых необязательных полей совместимым изменением не считается и в v1 допустимо. |
| Формат | JSON, кодировка UTF-8, заголовок `Content-Type: application/json` |
| Деньги | Целое число **копеек** (`price_kopecks: 349900` = 3 499,00 ₽). Дробных сумм в API нет (BR-09). |
| Время | ISO 8601 с часовым поясом, хранится и отдаётся в UTC: `2026-10-05T18:34:08.814520Z` |
| Авторизация | `Authorization: Bearer <access_token>`, раздел 5 |
| Трассировка | Каждый ответ содержит `X-Request-ID`. Клиент может прислать свой, иначе сервер сгенерирует. По нему ищут все записи одного запроса в логах. |
| Идемпотентность | `POST /orders` и `POST /orders/{id}/payments` требуют заголовок `Idempotency-Key` (UUID). Подробно — в 05-flows.md. `DELETE` идемпотентен по природе: повтор возвращает тот же 204. |
| Пагинация | `limit` (1–100, по умолчанию 20) и `offset` (с 0). В ответе — `items`, `total`, `limit`, `offset`. |

## 3. Формат ошибок

Все ошибки, бизнесовые и технические, приходят в одном формате:

```json
{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "Недостаточно товара на складе",
    "details": [{"product_id": 1, "requested": 10, "available": 3}]
  }
}
```

| Поле | Назначение |
|---|---|
| `code` | Стабильный машинный код. **Клиент выбирает поведение по нему**, а не по тексту. Коды не меняются без смены версии API. |
| `message` | Текст для человека. Может меняться, клиент не должен его разбирать. |
| `details` | Подробности, структура зависит от кода. Может быть `null`. |

Ошибки валидации приходят в том же формате, `details` — список полей:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [{"field": "quantity", "message": "Input should be less than or equal to 10"}]
  }
}
```

### 3.1. Коды ошибок (каталог, аккаунт, корзина)

| HTTP | `code` | Когда |
|---|---|---|
| 401 | `UNAUTHORIZED` | Нет заголовка `Authorization`, токен истёк, подделан, не того типа или пользователь удалён |
| 401 | `INVALID_CREDENTIALS` | Неверный email или пароль. Ответ одинаковый в обоих случаях (US-02 AC 2) |
| 403 | `FORBIDDEN` | Токен валиден, но роль не позволяет (покупатель вызывает `/admin/...`) |
| 404 | `NOT_FOUND` | Объекта нет: товар, товар в корзине, неизвестный адрес |
| 405 | `METHOD_NOT_ALLOWED` | Метод не поддерживается для этого адреса |
| 409 | `EMAIL_TAKEN` | Регистрация с уже занятым email (без учёта регистра) |
| 409 | `PRODUCT_INACTIVE` | Попытка положить в корзину снятый с продажи товар |
| 409 | `OUT_OF_STOCK` | Количество больше доступного остатка. `details`: `product_id`, `requested`, `available` |
| 422 | `VALIDATION_ERROR` | Тело или параметры запроса не прошли проверку формата |
| 422 | `CART_QUANTITY_LIMIT` | Добавление сделает количество товара в корзине больше 10 (BR-08) |
| 429 | `TOO_MANY_ATTEMPTS` | Больше 5 неудачных входов с одного IP за минуту. Заголовок `Retry-After: 60` |

### 3.2. Как выбираются коды HTTP

| Код | Смысл | Повторять запрос? |
|---|---|---|
| 200 / 201 / 204 | Успех: данные / создано / успех без тела | — |
| 401 | Не знаем, кто вы | После обновления токена (`/auth/refresh`) или входа |
| 403 | Знаем, кто вы, но нельзя | Нет |
| 404 | Нет такого объекта | Нет |
| 409 | Запрос корректный, но конфликтует с текущим состоянием данных | Только после изменения условий (уменьшить количество и т.п.) |
| 422 | Запрос некорректен сам по себе | Нет, сначала исправить запрос |
| 429 | Слишком часто | После `Retry-After` |
| 5xx | Ошибка сервера | Да, с паузой. Для `POST` — с тем же `Idempotency-Key` |

Проверки выполняются по слоям: сначала **схема запроса** (формат, типы, диапазоны → 422 `VALIDATION_ERROR`), затем **авторизация** (401/403), затем **бизнес-правила** в сервисе, для которых нужны данные из базы (404, 409, 422 `CART_QUANTITY_LIMIT`). Последний рубеж — ограничения в самой базе (`CHECK`, `UNIQUE`).

## 5. Авторизация

1. `POST /auth/login` возвращает пару токенов (JWT, подпись HS256 секретом сервера):
   - **access** — живёт 15 минут, передаётся в каждом запросе: `Authorization: Bearer <access_token>`;
   - **refresh** — живёт 30 дней, нужен только для `POST /auth/refresh`.
2. Получив 401 `UNAUTHORIZED` на обычном запросе, клиент вызывает `/auth/refresh` и повторяет запрос с новым access. Если и refresh вернул 401 — нужен повторный вход.
3. Содержимое токена (`sub` — id пользователя, `role`, `type`, `iat`, `exp`) читается кем угодно: это base64, а не шифрование. Секретов в токене нет.
4. На каждом запросе сервер проверяет подпись и срок токена, а **пользователя и его роль берёт из базы**. Поэтому смена роли или удаление пользователя действуют сразу, а не через 15 минут. Роль внутри токена для проверки прав не используется.

## 6. Аккаунт

### POST /auth/register — регистрация (US-01)

Тело:

```json
{"email": "Daria@Example.com", "password": "Secret123"}
```

- `email` — корректный адрес; сохраняется в нижнем регистре, поэтому `Daria@Example.com` и `daria@example.com` — один пользователь.
- `password` — 8–128 символов, хотя бы одна буква и одна цифра. Хранится только bcrypt-хеш.

Ответ **201**:

```json
{"id": 5, "email": "daria@example.com", "role": "customer", "created_at": "2026-10-05T18:30:00Z"}
```

Ошибки: 409 `EMAIL_TAKEN`, 422 `VALIDATION_ERROR`.

### POST /auth/login — вход (US-02)

Тело: `{"email": "...", "password": "..."}`. Ответ **200**:

```json
{"access_token": "eyJ...", "refresh_token": "eyJ...", "token_type": "bearer"}
```

Каждый вход выдаёт новую пару. Ранее выданные токены продолжают действовать до своего срока (вход с нескольких устройств).

Ошибки: 401 `INVALID_CREDENTIALS`, 422 `VALIDATION_ERROR`, 429 `TOO_MANY_ATTEMPTS`.

### POST /auth/refresh — новый access-токен

Тело: `{"refresh_token": "eyJ..."}`. Ответ **200**: `{"access_token": "eyJ...", "token_type": "bearer"}`. Новый refresh не выдаётся.

Ошибки: 401 `UNAUTHORIZED` (токен истёк, подделан, это не refresh, пользователь удалён), 422.

### GET /users/me — профиль

Ответ **200** — как при регистрации. Ошибки: 401.

## 7. Каталог

Методы каталога доступны без авторизации. Снятые с продажи товары (`is_active = false`) в каталоге не видны.

### GET /categories — дерево категорий

Ответ **200** — список категорий верхнего уровня, у каждой вложенный список `children`:

```json
[{"id": 1, "name": "Смартфоны и гаджеты", "parent_id": null,
  "children": [{"id": 2, "name": "Смартфоны", "parent_id": 1, "children": []}]}]
```

### GET /products — список товаров (US-03)

| Параметр | Тип | Описание |
|---|---|---|
| `category_id` | int | Категория **вместе со всеми подкатегориями** |
| `price_min`, `price_max` | int ≥ 0 | Цена от / до, в копейках, включительно |
| `q` | string ≤ 100 | Поиск по названию без учёта регистра |
| `sort` | `newest` / `price_asc` / `price_desc` | По умолчанию `newest` |
| `limit`, `offset` | int | Пагинация, раздел 2 |

Ответ **200**:

```json
{
  "items": [{"id": 1, "sku": "PH-VOLT-X1", "name": "Смартфон Volt X1 128 ГБ", "category_id": 2,
             "price_kopecks": 3499000, "available": 21, "in_stock": true}],
  "total": 12, "limit": 20, "offset": 0
}
```

`available` = остаток на складе минус резервы неоплаченных заказов. `in_stock` = `available > 0`.

Ошибки: 422 `VALIDATION_ERROR`.

### GET /products/{product_id} — карточка товара (US-04)

Ответ **200** — поля списка плюс `description`. Ошибки: 404 `NOT_FOUND` (нет товара или он снят с продажи), 422.

## 8. Корзина

Все методы требуют авторизации. У покупателя одна корзина, она создаётся при первом добавлении. **Корзина не резервирует товар**: резерв ставится только при оформлении заказа (US-07). **Цены в корзине текущие**; цена фиксируется в заказе (BR-02).

Все изменяющие методы, кроме `DELETE`, возвращают корзину целиком:

```json
{
  "items": [{"product_id": 1, "name": "Смартфон Volt X1 128 ГБ", "quantity": 3,
             "price_kopecks": 3499000, "line_total_kopecks": 10497000,
             "available": 1, "is_available": false}],
  "total_kopecks": 10497000,
  "has_unavailable_items": true
}
```

`is_available = false`, если товар сняли с продажи или его доступный остаток стал меньше количества в корзине. Такая позиция **не удаляется автоматически** (US-06 AC 3): покупатель сам уменьшает количество или удаляет её. Оформить заказ с такой позицией не получится.

### GET /cart — корзина

Ответ **200**. Пустая корзина: `{"items": [], "total_kopecks": 0, "has_unavailable_items": false}`. Ошибки: 401.

### POST /cart/items — добавить товар (US-05)

Тело: `{"product_id": 1, "quantity": 2}`, `quantity` 1–10, по умолчанию 1. Если товар уже в корзине, количество **прибавляется**.

Ответ **201** — корзина.

| Ошибка | Когда |
|---|---|
| 404 `NOT_FOUND` | Товара нет |
| 409 `PRODUCT_INACTIVE` | Товар снят с продажи |
| 409 `OUT_OF_STOCK` | Итоговое количество больше доступного остатка |
| 422 `CART_QUANTITY_LIMIT` | Итоговое количество больше 10 |
| 422 `VALIDATION_ERROR` | `quantity` вне 1–10 или не число |

### PATCH /cart/items/{product_id} — изменить количество (US-06)

Тело: `{"quantity": 3}`, 1–10. Количество **заменяется** на указанное.

Ответ **200** — корзина.

Ошибки: 404 `NOT_FOUND` (товара нет в корзине), 409 `OUT_OF_STOCK` (больше доступного остатка, с v0.2 требований), 422 `VALIDATION_ERROR`.

### DELETE /cart/items/{product_id} — удалить позицию (US-06)

Ответ **204** без тела — и когда позиция была, и когда её уже нет. Повтор безопасен (идемпотентность), поэтому клиент может повторять запрос после сетевой ошибки.

## 9. Известные проблемы и ограничения

| # | Проблема | Риск | Статус |
|---|---|---|---|
| 1 | Swagger описывал ошибку 422 в стандартном формате FastAPI `{"detail": [...]}`, а API отвечает `{"error": {...}}`. Клиент, написанный по документации, не нашёл бы текст ошибки. | Средний | ✅ Исправлено 2026-10-06: схема `ErrorResponse` в OpenAPI для всех ответов 4xx, ошибки описаны у эндпоинтов каталога, аккаунта и корзины; тест `test_openapi_documents_real_error_format` |
| 2 | `PATCH /cart/items` не проверял остаток, `POST` — проверял (противоречие US-05 AC 4 и US-06 AC 1). | Средний | ✅ Исправлено 2026-10-05: требования v0.2, код, тест `test_cart_update_respects_stock` |
| 3 | Выданные refresh-токены нигде не хранятся и не отзываются. После смены пароля или выхода старый refresh работает до 30 дней. | Высокий для прода | Открыто. Решение: таблица refresh-токенов с отзывом и ротацией или `password_changed_at` у пользователя и сравнение с `iat` токена |
| 4 | Регистрация раскрывает, что email уже зарегистрирован (409 `EMAIL_TAKEN`), хотя вход это скрывает. | Низкий | Принято осознанно ради удобства. Строгий вариант — всегда «проверьте почту» |
| 5 | Вход для несуществующего email отвечает быстрее, чем для существующего (bcrypt выполняется только во втором случае): по времени ответа можно узнать, зарегистрирован ли email. | Низкий | Открыто. Решение: при отсутствии пользователя проверять пароль с фиктивным хешем |
| 6 | Лимит неудачных входов хранится в памяти процесса API. При нескольких экземплярах API лимит считается в каждом отдельно и сбрасывается при перезапуске. | Средний для прода | Открыто. Решение: счётчик в Redis |
| 7 | Корзина показывает новую цену, но не предупреждает об изменении цены при оформлении заказа. | Низкий | Открытый вопрос бизнесу (02-requirements, раздел 7) |
| 8 | `product_id` больше максимума `BIGINT` проходит проверку схемы, а база его не принимает. Ожидаемо 500 вместо 404/422. | Низкий | Не проверено. Решение: ограничить `product_id` в схемах (`le=2**63-1`) |
